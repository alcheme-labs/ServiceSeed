<a id="document-boundaries"></a>
## 范围与约束力

本协议面向独立实现原子服务、服务宿主及维护 Agent 接入的开发者，规定各方为安全运行、维护和互通必须共同理解的含义与行为。实现者无需了解特定项目、业务场景或讨论历史。

核心约定适用于遵循本协议的实现；可选能力在声明或实际提供时承担相应义务。具体业务含义、承诺和适用条件由服务契约确定，授权来自有权主体。内部组件、技术栈与部署方式可以不同，授权、履约和结果真实性要求不能因此省略。

本文中的必须、不得及相应行为要求属于协议约定；标明待定的细节尚未形成完整约定。[最小交互约定](#minimum-interaction)与[完整流程](#minimum-flow)规定信息含义、前置条件和可观察结果，不规定组件或接口划分。实现者仍须共同采用一份明确的调用绑定说明，并验证实际行为；本草案不以语义约定代替已完成的传输映射或互通验收。

<a id="product-core"></a>
## 服务模型与目标

**AI 遵循共同规则，在用户的服务空间中创建原子服务；每个服务具备明确能力、持续运行状态和受控的 Agent 维护能力，并能在授权范围内与其他服务互通、组合。**

服务能够在授权范围内调整自身实现，并持续维护对调用方的承诺。

- **原子化**：按独立业务能力划分，可独立识别、运行、授权、维护和组合；完整业务流程也可以是一个长期服务，内部步骤由服务定义，不按单次请求或内部步骤机械拆分。可以声明依赖，不表示跨服务事务天然具备原子性。
- **智能化**：Agent 属于服务的生命周期，依据该服务的目标、状态和授权维护实现。每个服务有独立维护上下文，模型可按需唤起或共享，实例之间的权限和状态必须隔离。
- **互通**：共同约定服务怎样描述能力、证明身份、核验授权、调用、表达结果和处理变化；内部语言、模型与实现方式可以不同。

**实现可以变化，服务承诺必须有验收依据，权限不能被静默扩大。** 协议统一可观察的行为，由运行环境及原资源所有者执行约束，不能只靠 AI 声称遵守。普通请求可以执行已启用实现，不要求模型逐次参与。

<a id="protocol-boundaries"></a>
## 协议颗粒度与核心、可选能力

**共同必需规则，加上可声明的可选能力；服务只承担其实际提供能力对应的义务。** 核心原则不等于所有实例必须部署相同模块。规则须能被独立实现一致理解和检查，不能只靠能力同名；具体字段、调用绑定与尚未定案的交互细节继续标为待定。

| 归属 | 应确定什么 | 不替代什么 |
| --- | --- | --- |
| 通用协议 | 独立服务与宿主为安全调用、组合和维护必须一致理解的身份、能力描述、契约版本、授权、成功/失败/未完成及受控维护行为 | 不规定具体业务内容、固定包装层型或统一内部记录表 |
| 服务契约 | 本服务的业务含义、状态责任、依赖和包装关系、对外承诺、适用条件及查询/恢复保证；授权范围来自有权主体 | 不能自授权限、绕过共同约束或静默降低已接受的承诺 |
| 具体实现 | 在契约与授权内选择代码、编排、进程、存储、消息和部署方式，实际落实共同规则 | 不能把授权、结果真实性或已承诺的一致性当成可自行省略的内部细节 |

- **核心必需。** 服务边界、按共同协议互通与组合、全过程授权，以及包装/组合后仍是同协议服务的递归原则。单个实例不必有子服务或包装层。[原子服务要求](#atomic-service)、[受控创建与维护](#agent-boundary)、[必要维护上下文](#maintenance-context)及[共同运行逻辑](#lifecycle)仍是核心。
- **可选服务能力。** 共同上下文可以由普通服务提供，复用适用的读取、更新、授权与版本规则；共享内容、结构和业务校验归该服务契约。它不成为全局知识库或其他服务运行状态的默认保存者，也不接管已有业务权威。共享上下文与维护 Agent 必须获得的本服务授权上下文分别处理。
- **可选通用交互能力。** 订阅/通知、同步/订阅恢复按需声明；声明支持后，必须遵守对应的共同语义和本服务承诺。订阅需说明订阅、取消、通知及授权失效的含义；声明可恢复订阅或状态同步时，需说明当前状态与后续更新的衔接、版本/新鲜度、重复或遗漏识别，以及补齐或重新取得状态的恢复行为。具体事件、范围、保留期限和交付承诺归契约，传输与一致性实现不在此选定。
- **一般运行恢复仍是核心。** 有持续处理或持久效果的操作，应有可识别和查询的操作/结果、中断后确认结果与安全接续行为。这不以提供订阅能力为前提，也不要求每个服务保存同一种流程/协作记录或拥有独立数据库；具体状态含义与恢复承诺归契约，必要持久状态复用明确负责方。

调用、读取、更新、订阅和结果/通知交付按实际提供的能力分别落实当前授权；组合或包装不自动获得内层资源、内部日志或维护权限。未知的必需能力与不兼容承诺不能静默忽略。固定所有服务的层数/层型、强制全局共享状态、建立第二业务权威，或允许 Agent 改写授权和验收来维持可用，均偏离本协议方向。

<a id="atomic-service"></a>
## 一个原子服务必须具备什么

以下是遵循本协议的原子服务应满足的最低语义要求；具体字段和接口仍待收敛。

| 必备部分 | 必须能说明什么 |
| --- | --- |
| 身份与责任人 | 稳定服务身份、所属空间、有权控制者及维护责任人；服务身份、对外契约版本和实现版本分别标识 |
| 能力与承诺 | 提供哪些业务能力、输入输出及其含义、适用条件、副作用和失败语义；哪些承诺可自动验收、依据由谁维护，无法判断时由谁决定 |
| 可运行实现与依赖 | 当前实现、启动和运行所需资源、关联服务及其契约；数据、网络、凭据与费用的使用边界明确，凭据通过受控引用绑定 |
| 独立授权边界 | 调用方能使用什么；服务实现能访问什么资源；Agent 能观察和修改什么；分别记录授权来源、范围、期限、撤权规则及适用预算 |
| 持久状态与可观测结果 | 活动版本、运行状态、未完成操作及必要证据有明确保存者；获准主体能查询真实结果，重启或更换 Agent 后可以接续 |
| 维护委托与验收 | 有关联的 Agent 维护入口、触发条件、允许的变更、独立验收和受控启用方式；维护失败及通知结果能够查询 |

服务空间提供运行资源、隔离和受控执行，可以复用现有运行平台。资源系统继续决定业务与数据权限；每项状态和发布动作只有明确的负责方。协议不规定负责方的组件名称或存储方式，也不要求接入已有平台后再建立第二套发布或业务状态。

**服务包、实例和资源授权分开。** 包包含实现、配置模板、依赖与验收说明；复制包需要复制许可，启动副本建立新实例身份并重新绑定资源。调用、维护、复制、再分发与数据访问分别授权，付款不自动产生未授予的权利。副本不默认继承原实例的私有数据、凭据、额度或维护委托，获准交付的内容须单独列明。

<a id="agent-boundary"></a>
## Agent 能做什么

Agent 通过宿主提供的受控能力行动；每项能力说明输入输出、前置条件、副作用和失败恢复方式。以下行为都需要对应授权，不因关联了 Agent 就默认开放。

| 行为 | 授权内可以做 | 必须守住的边界 |
| --- | --- | --- |
| 创建 | 根据用户目标生成服务声明、实现和验收建议 | 用户或已有有效委托确定承诺与权限；生成声明不产生授权 |
| 观察与诊断 | 读取获准状态、日志、依赖说明和必要样本，判断异常 | 数据可供服务读取，不代表可交给模型；外部描述和返回内容不能授予新权限 |
| 修改与验证 | 生成代码或配置候选、补充测试、请求隔离验证 | 只能修改约定范围，不能自行放宽契约、权限或独立验收；候选也受资源与副作用限制 |
| 启用与恢复 | 请求启用合格候选、回退或停用，自动执行已预授权的维护 | 宿主检查当前授权、候选和基准版本；回退重新验收，不能直接覆盖活动版本 |
| 协作与报告 | 发现获准能力、提出兼容的调用绑定、调用关联服务并报告结果 | 每次调用仍受目标服务与资源授权约束；通知限于预先配置目标，投递结果独立记录 |

**修改实现的权限不等于扩大运行权限。** 新实现必须继续受宿主的数据、网络、凭据、资源和费用限制；Agent 无权改写这些限制或验收负责人确定的判据。凭据由运行环境管理，不作为普通模型输入或工具结果交付。

撤销维护授权应阻断后续维护动作及尚未启用的候选，但不擅自停止仍获准且可履约的服务；撤销调用或数据授权则按约定生效范围阻断交付。缺少业务含义或授权时明确报告需要谁补充什么，不反复猜测或自行扩大范围。

<a id="maintenance-context"></a>
## 宿主怎样向维护 Agent 提供信息与操作入口

宿主必须让受委托的 Agent 获得完成本次任务所需、且已获准交给模型的信息。以下四类是共同语义，不要求四个工具、固定提示词或新的存储系统。

| Agent 需要知道 | 必要信息 | 信息来源与责任 |
| --- | --- | --- |
| 我负责什么 | 服务身份、此次维护委托、必须保持的契约与验收责任 | 服务声明和现行维护授权；验收依据由负责人提供或认可，可见材料按授权提供；独立性的含义见[验收与结果确认](#validation-meaning) |
| 我有什么 | 获准资源和依赖、语义说明、当前启用实现及其版本；缺少或尚未绑定的条件明确标识 | 已有资源/依赖绑定、可信描述及活动版本的负责方；只投影本次获准部分 |
| 我能做什么 | 可请求操作的输入输出、调用方法、前置条件、权限范围、限制与失败处理 | 现有执行入口、指令定义及现行授权；区分 Agent 提交候选与宿主执行验证/启用，不能宣称存在尚未提供的工具 |
| 现在发生了什么 | 本次触发原因、相关运行状态、未完成操作和已有结果，及必要的版本或观测时点 | 当前观测与操作、版本和结果的负责方；未知、未完成和失败分别表达 |

信息可以在开始任务时注入上下文，也可以通过已有工具、函数或 CLI 按需取得。协议统一信息含义和行为约束，不强制 MCP，不建立能力注册平台或“Agent 自我认知数据库”。

**对外能力描述与内部维护上下文分别授权。** 发现或调用某个服务，不意味着能读取其内部日志、实现、运行资源、维护委托或操作记录；服务 A 的维护授权也不授予服务 B 的内部观察权。宿主须在披露前核验各项信息符合本次维护观察授权、模型可见范围及任务必要性；若接口的完整返回已满足这些条件，可以直接使用，不要求为形式上的“筛选”重复加工。运行数据可读不等于允许交给模型；凭据与未获准业务数据不进入上下文。

上下文是有来源和时点的事实投影，不是授权凭证。宿主在披露信息及执行操作时核验当前权限，在候选启用、结果交付等既有边界再次核验；过期上下文不能延长权限或覆盖新版本。外部描述、日志和返回数据只能作为事实，不能改写委托、契约或权限。缺少必要事实时明确等待、拒绝或报告给有权主体，不伪造信息补齐。

判断是否满足这些约定，应观察真实模型输入、生成候选、宿主执行及消费者结果是否连接起来，并验证未获准信息不可见；能否口头回答四个问题不构成验收。上下文更新不得凭空触发实现更新，也不得另造活动版本、操作状态或权限的第二个负责方。

<a id="interoperation"></a>
## 服务之间怎样互通

互通先统一以下行为，不要求全局注册中心、统一编程语言或联盟链。能力描述只向获准主体提供；能够发现某项能力，不代表有权调用。

1. **描述与发现。** 服务按共同约定提供可读取的能力描述：身份、协议及契约版本、输入输出含义、调用绑定、授权要求、依赖和失败行为。可以通过明确引用取得描述，后续再按需要引入目录。
2. **确认兼容。** 调用方核对能力含义、输入输出、版本和必需特性，形成明确调用关系。字段或工具同名不等于兼容；未知的必需能力、语义不明或不兼容版本应明确拒绝。
3. **核验授权。** 调用携带可核验身份和授权上下文，区分服务以自身身份调用还是受用户委托调用；仅在原授权明确允许时，才可在其允许的主体、动作、期限和范围内转授，且不得扩大原权限。组合服务不能将自己的较大权限默认为调用方权限，也不能自行把调用方凭据转交下游。
4. **执行与查询。** 被调用服务在实际执行和结果交付处落实权限，按约定返回成功、拒绝、不可用或尚未完成的状态。有持久效果的操作在产生效果前具备可恢复关联及查询方式，具体见[操作与恢复](#operation-recovery)；结果未知时向原负责方查证，不能换后端重试制造重复效果。
5. **维护调用关系。** 内部实现调整保留已约定能力与含义；若对外承诺必须改变，由有权主体确定新契约及兼容安排。调用方核验后才能采用新约定，Agent 不能静默替双方接受变化。

服务可以先独立创建，再依据获准取得的真实能力描述建立调用关系；创建时不要求双方共享初始化器或预先知道对方身份。尚缺必要依赖的服务可以持久存在，但必须准确报告待绑定或不可用。绑定只使用已有有效授权，不能由描述、模型判断或绑定动作自行生成授权；关系确认须完成身份、授权、契约与绑定兼容检查，并按[验收与结果确认](#validation-meaning)验证受影响承诺及消费者结果。仅保存连接配置不算关系已确认；重启继续使用已确认关系时仍须核验当前权限。

组合必须遵守下游数据的使用和交付范围，包括缓存及派生结果的约定；不得通过组合绕过限制。撤权不能抹去接收者另存的明文副本，只允许计算结果的场景需要限制原始数据与结果出口。

共同语义需要落到可测试的调用绑定才能互通。互通双方须采用共同支持的绑定和输入输出约定，不能仅凭工具同名宣称兼容。传输方式不改变业务权限、结果真实性或履约责任。

<a id="minimum-interaction"></a>
## 最小交互约定

服务提供方对自己的能力描述、执行和结果负责；调用方对自己接受的调用关系及下游使用负责。各方现有的授权负责方决定谁可以执行或查看什么。维护 Agent 提交获准的候选和请求，服务宿主或其已有发布负责方核验并启用，效果负责方保存和确认操作结果。这里区分责任，不要求不同进程、独立组件或每次都由真人批准；已有有效委托可以覆盖自动执行。

下表定义共同语义，不是固定字段名、消息编码或工具清单。一个入口可以承接多个动作，一个动作也可经多次交互完成；合并或拆分不能跳过前置条件。

| 交互内容 | 必须能共同确定的信息与行为 |
| --- | --- |
| 选定调用绑定 | 双方明确采用同一份可取得的绑定说明及其版本。该说明给出本文逻辑信息到字段、编码和入口的映射，以及身份/授权证明的承载与核验方式、结果/错误表达和恢复范围；可引用已有机制，不要求另建协议或注册平台 |
| 取得能力描述 | 明确目标服务身份、采用的协议版本、能力和特定契约版本、输入输出含义、必需特性、支持的绑定及权限要求。描述来源与目标身份的对应关系须可核验；描述本身不授予调用权 |
| 核验身份与授权 | 明确实际执行主体、以自身身份还是代表另一主体、目标服务/资源、动作和范围，以及获认可的授权来源、有效条件和撤权要求。执行方按其现有可信授权来源核验，不接受仅自称的身份或权限；原始凭据不因此进入模型上下文 |
| 确认调用关系并调用 | 调用方能恢复识别所接受的目标、能力、契约版本、绑定及授权适用范围。调用不得静默换用另一契约；输入和结果须对应本次请求。关系不产生新授权，也不要求双方另建同一份关系数据库 |
| 提交候选并请求启用 | 明确目标服务、维护委托、候选内容或可核验引用、基准实现版本、要保持的契约及影响验证的依赖条件。验证结果须对应这份候选和这些条件；请求启用不等于允许启用或已经生效 |
| 查询持久操作结果 | 按[可恢复关联](#operation-recovery)定位原操作，在当前查询/披露权限内取得其真实结果及必要证据引用。已启用版本、消费者结果确认和当前服务状态分别表达；查询不会重新执行原操作 |

**兼容性不是按名称猜测。** 双方须支持所选协议和绑定版本，以及本次能力声明的全部必需特性。对外调用采用已接受的特定契约版本；替换版本只有在调用方有权接受、且兼容依据明确时才可使用，版本号相近不构成依据。未知必需特性、含义不明或无共同绑定时拒绝建立关系。可忽略的扩展必须由绑定明确为可选，且忽略后仍满足既有承诺。

所选绑定还须明确操作关联的作用域、有效范围、结果可查询及防重复效果的承诺，不能自行改变本文的状态含义或权限边界。正文尚未指定一份通用于所有传输的具体字段/入口映射；双方各自声称遵循本节，不等于已采用相同绑定。

<a id="lifecycle"></a>
## 共同运行逻辑

**目标与授权 → 生成候选 → 独立验证 → 受控启用 → 调用方使用 → 观察变化 → Agent 调整候选 → 再验证与启用。** 创建和维护复用同一过程。

这里约定受控变更的行为与前置条件，不固定内部状态名、类、进程或存储表。

- 验收由负责人提供或认可，Agent 可以补充检查，不能自行降低成功标准。验证绑定具体候选、契约和依赖条件；启用前重查授权及当前版本，过时候选不能覆盖新版本。
- 已接受、已验证、已启用和实际可用分别表达；从调用方真实入口确认结果后才报告恢复。服务可用性与维护进度分开，维护中不意味着旧版本已停止。
- 运行环境负责持久化和接续，重复提交、并发、重启及超时不能重复产生效果。回退也须满足当前权限、数据和契约；涉及持久状态变化的候选必须说明兼容及恢复方式，不能把代码回退当成数据恢复。
- 无法恢复时，保留仍可履约的实现，否则明确不可用并交给有权负责人。安全拒绝属于正确处理失败，不能计作恢复成功。

<a id="validation-meaning"></a>
### 独立验收与消费者结果确认

**独立验收保护的是判据控制权与结果真实性。** 生效判据由有权负责方提供或认可；生成候选的 Agent 不能自行改变这些判据，也不能以自己的“通过”声明代替真实执行结果。独立性不要求另一个模型、独立进程或每次人工确认。获准公开的业务样例、测试和预期结果可以提供给 Agent；隐藏测试是可选验收手段，未获准的验收数据仍不得披露。

新建或修改调用关系时，检查目标身份、当前授权、所选契约和绑定兼容性，并验证受影响的服务承诺及其依赖条件。维护候选改变了验证所依据的条件时，重验受影响部分；可以复用仍有效的证据，不一概要求重跑所有检查，也不能仅凭结构校验代替业务正确性确认。

**消费者结果确认（本文亦称读回）** 是沿约定身份、授权和调用路径取得真实结果，核对其来源、所用版本或相关条件，以及是否符合受影响的承诺。可以复用实际调用响应、原操作结果或获准的受控验证结果，不要求额外查询接口或额外业务调用；不得仅为验证而重复产生业务效果。关系配置已保存、候选检查通过或启用已受理，都不能单独证明消费者结果已恢复。

<a id="operation-recovery"></a>
## 持久操作与响应丢失后的确认

本节适用于产生持久效果的请求，包括调用关系的保存和维护候选启用；不要求纯读取请求拥有持久操作记录。操作关联、结果和效果复用原负责方，查询者不能以自己的缓存、会话或模型推测替代原负责方的确认。

1. **效果发生前可关联。** 请求方在首次可能产生效果的提交之前，须已持有或能够恢复取得足够的关联信息，使接收方及获准查询者能定位同一逻辑操作；不能只依赖可能丢失的首次响应。可以复用现有请求/操作引用，或明确约定的候选与前置条件组合，不强制新增一种标识或记录系统。需要跨重启恢复时，关联本身也须可恢复。
2. **重试与新操作可区分。** 关联须绑定目标、原执行主体、动作、业务内容及必要前置条件；相同关联但这些内容不同，作为冲突拒绝，不能覆盖原请求。相同参数不自动等于同一逻辑操作，新的合法意图须能与重试区分。重试须重新核验当前权限；关联本身不授予执行或查看权。
3. **重复提交不重做已生效效果。** 在声明的有效范围内，同一操作的重复或并发请求须关联到原操作。已生效时保持原结果，未完成时按原操作安全接续；当前版本已变化不能把先前成功改写成失败。只有接收方能够保证同一关联不会产生重复效果时，才允许以该关联重试；否则先查询，无法确认时保持未知，不能通过换标识、换后端或换执行者绕过。
4. **查询只确认，不重新执行。** 查询时核验当前查看及披露权限；结果须说明所定位操作、真实进展/效果及必要的版本或证据关联。原操作有权执行，不表示查询者永久有权查看；查询被拒绝不改变原操作结果，由仍获准主体按既有权限查证，不能为恢复自动续权。
5. **恢复范围须提前明确。** 绑定或契约说明关联的作用域、有效范围以及结果查询和防重复效果的保留承诺，不在此统一期限。超出承诺范围或原记录无法取得时，明确不能确认；不得把无法判定是否已执行的原请求当成新请求执行，也不能把未终结操作的在途请求当成新操作重新接受。

以下是必须可区分的结果含义，不要求实现采用这些内部状态名或同一种状态机：

| 原操作结果 | 可以推断什么 | 恢复行为 |
| --- | --- | --- |
| 未完成 | 已受理或执行中，尚无最终效果结论 | 查询或在原关联下安全接续，不另开一次同义操作 |
| 已生效 | 原负责方确认约定效果已发生；候选启用结果能对应实际启用版本 | 复用原结果；是否已完成消费者结果确认另行表达 |
| 确认未生效 | 原负责方能确认操作被拒绝或失败，且约定效果没有发生 | 如需再次尝试，遵守已声明的重试规则和当前授权；改变意图须作为新操作 |
| 结果未知 | 尚不能确认原请求是否受理或效果是否发生 | 向原负责方查证，不报告成功或未执行，不盲目重投 |

超时、无权查询、查询暂不可达、查无记录或记录过期，都不能单独证明原操作未执行。原操作已生效、该版本的消费者结果已验证、服务当前是否可用是不同事实；后来又启用了其他版本时，保留原操作的真实结果，不能用当前活动版本或后来恢复的结果倒推原候选已经验证成功。

<a id="minimum-flow"></a>
## 最小流程：授权调用、维护启用与结果恢复

以下使用通用角色：S 为被调用服务，C 为调用服务，M 为 S 的维护 Agent，H 为 S 的宿主或已有发布负责方。角色可以由同一运行环境承接，授权仍分别核验。K 表示已接受的特定服务契约，B 表示共同选定的调用绑定，P 表示候选，V0/V1 表示基准/启用实现版本，O 表示可恢复的启用操作关联；这些记号不是强制字段名。

| 步骤 | 交互与检查 | 完成条件或失败处置 |
| --- | --- | --- |
| 1. 取得并核对描述 | C 经获准入口取得 S 的可信能力描述，确认目标身份，并选择自己支持的 K、B 及必需特性 | 无法核验来源、含义不明或不兼容则拒绝；可发现不等于可调用 |
| 2. 准备授权关系 | C 提供已有有效授权依据，或由 S 的现有授权负责方按其规则授予；S 核验实际主体、委托关系、具体动作与范围 | C 保存或复用待确认关系及所选 K/B；这一步不自行增加授权，缺必要条件时保持待确认或拒绝 |
| 3. 确认关系并使用 | C 沿所选绑定真实调用 S，S 在执行与结果交付处核验权限；完成受影响承诺的验证及消费者结果确认 | 通过才确认关系可用，重启可恢复识别；未通过如实报告待确认或不可用。该结果可来自已发生的正常调用，不要求额外业务调用 |
| 4. 形成维护候选 | S 需要调整实现时，H 向 M 提供获准上下文；M 提交 P、要保持的 K、基准 V0 和相关依赖条件；H 按负责人认可的判据验证 | 候选与证据可对应；验证不通过不启用，M 的自报通过不替代 H 的核验 |
| 5. 请求并执行启用 | 首次启用请求前，请求方与 H 已能凭 O 关联此请求。H 重验维护授权、P 的验证依据、V0 与相关依赖条件，再由已有发布负责方完成受控启用 | 权限失效、基准或依赖条件变化时不以旧验证强行启用；成功则保存 O 对应 V1 的真实效果及后续结果确认状态 |
| 6. 首次响应丢失 | M 或获准接续方未收到响应，凭 O 向 H/原效果负责方查询，而不是新建一次启用来猜测 | 查询区分未完成、已生效、确认未生效、未知，以及此次查询无权或不可达；按上一节处理，不因超时认定失败 |
| 7. 确认恢复后的使用 | 获准方确认 O 的实际结果，并取得经约定调用路径产生的消费者结果；C 继续采用原 K/B 和现行授权使用 S | 启用生效且相关消费者结果符合原承诺，才报告维护恢复完成；只有启用证据时保留待确认，查询拒绝不等于启用失败 |

若授权在步骤间变化，后续执行或交付按当前授权阻断，先前真实效果仍保留；维护失败时，仅继续运行仍获准且可履约的实现。各步骤可由已有入口合并或自动推进，所需关联也可复用既有记录；流程不要求新的管理服务、固定工具数量或额外业务平台。

<a id="onion-layers"></a>
## 递归洋葱包装与降挡边界

**洋葱是可递归、按需组合的服务包裹关系，层数、每层职责与组合方式不由通用协议写死。** 核心能力外可以包装鉴权服务，再按需增加其他能力；某层本身可以是遵守同一协议的服务。多个服务组成网络后，也可作为同协议组合服务对外提供能力，继续被包装或组合。不要求每个实例采用包装，也不要求每层独立进程。

共同规则要求包装与组合仍保持明确身份、可核验授权、对外承诺、状态责任和失败语义。具体层的组成、顺序及依赖由服务契约说明；请求、结果和失败怎样穿越各层，需要有可检查的约定，具体表达仍待细化。鉴权等必需前置条件不能被未授权绕过，包装也不自动取得内层维护上下文；描述的可见范围仍受各自授权约束。

**可以减少可用能力，不能自动降低授权或履约要求。** 每项操作的必要依赖、离线条件、撤权及证据新鲜度、数据时效和成功标准，由有权主体事先确定。

| 依赖故障 | 允许的处理 | 不能放宽的边界 |
| --- | --- | --- |
| 模型或维护 Agent 不可用 | 继续运行仍获准且可履约的实现，记录未完成维护 | 不跳过必要验证，不把未修复称作已恢复 |
| 其他依赖不可用，操作无需其新确认 | 满足原授权的离线条件、撤权检查、数据时效及必要依赖时继续 | 不延长授权，不以过期或不完整数据伪装成功 |
| 操作需要新授权或外部负责方确认 | 等待或明确不可用；已提交的保留操作标识查证 | 不擅自改单方批准，不先执行后补授权，不以本地状态代替外部成功 |
| 仅可选辅助记录延迟，或操作结果未知 | 前者按原约定持久保存并标明待补充；后者向原权威查询或幂等恢复 | 必需确认不得改成可选，排队不等于完成，未知不等于失败 |

调用与数据权限、维护范围、复制及再分发许可、有效期与撤权条件、数据含义与完整性、独立验收、必要确认、结果真实性和幂等性不能降级。旧数据、部分结果或较低运行标准只有原契约允许且对调用方明示时才可采用。暂停或不可用承认了暂时无法履约，不改变承诺。

每项事实只有明确的权威；由外部系统负责的事实，本地只保留请求和结果投影。更换权威必须处理在途操作、旧证据和权限，不能作为故障时的自动后备路径。外部接收或辅助凭据不能代替有效提交和业务读回。

<a id="open-questions"></a>
## 待明确的协议细节

- 最小流程的共同信息与行为以上文为准；其具体字段、编码、入口及认证机制的映射尚须形成双方可共同采用的调用绑定说明。该说明不得重新定义本文的授权、结果与恢复语义；绑定的实际互通须由独立实现验证。
- 上下级共同上下文怎样共享、是否继承或覆盖，以及服务依赖共享上下文时的行为，尚未确定；不默认继承权限，也不默认共享服务接管其他状态权威。
- 包装层的组成/顺序如何共同表达，请求、结果和失败穿层及必要前置条件的具体核验方式，仍需细化；本协议采用递归原则，不由此冻结内部执行结构。
- 订阅/取消/通知、同步版本与恢复的具体交互表示，以及不同服务怎样声明交付、新鲜度和恢复保证，仍待讨论。撤权的具体生效策略由授权规则与服务契约确定，不在此统一秒数，也不选数据库、消息系统或传输实现。

本节保留未定细节，不据此固定组件、技术栈或具体实现；草案中的原则不表示任一实现已经提供这些能力。
